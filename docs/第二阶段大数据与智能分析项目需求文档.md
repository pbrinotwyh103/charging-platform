# 电动汽车充电桩应用管理平台第二阶段项目需求文档

## 1 文档说明

### 1.1 编写目的

本文档规定电动汽车充电桩应用管理平台接入大数据可视化大屏和机器学习智能分析子系统后的业务范围、功能要求、数据要求、接口要求、非功能要求及验收标准，作为第二阶段设计、开发、联调、测试和验收的统一依据。

第二阶段不替换第一阶段的用户端、管理端、服务端和 SQLite 业务链路，而是在现有业务数据基础上增加离线数据治理、分层统计、Web 可视化和负荷预测能力，并将预测结果进一步反馈给用户端和管理端。

### 1.2 文档范围

本文档覆盖以下内容：

- 第一阶段系统与第二阶段系统的集成边界。
- 大数据采集、质量检测、清洗、存储和数仓加工。
- Web 端大数据可视化大屏。
- 机器学习负荷预测与模型指标展示。
- 用户端低拥堵站点推荐和管理端负荷预警。
- 接口、安全、性能、部署、测试和验收要求。

本文档暂不规定具体负责人和人员分工。

### 1.3 需求表述约定

- “应”表示必须满足的需求。
- “宜”表示建议满足、允许根据进度裁剪的需求。
- “可”表示扩展能力，不作为基础验收的阻断条件。
- 标记为 P0 的需求属于核心链路，P1 属于重要完善项，P2 属于后续优化项。

## 2 项目背景与建设目标

第一阶段已经形成用户端、管理员端、后台服务和 SQLite 数据库组成的充电业务平台，覆盖账户、站点、电桩、预约、充电、订单、钱包、告警和运营管理等业务。第二阶段利用历史充电数据、设备运行数据、用户行为数据、天气和节假日数据，建设大数据可视化大屏和机器学习智能分析子系统。

第二阶段应达到以下目标：

1. 建立从第一阶段数据到大数据分析数据的可重复处理链路。
2. 发现并隔离重复、缺失、越界、格式错误和引用失效等数据质量问题。
3. 建立 ODS、DWD、DWS、ADS 分层数据体系，统一统计口径。
4. 通过 Web 大屏直观展示营收、订单、负荷、设备、告警、区域和数据质量指标。
5. 基于历史时序数据预测未来 1 小时、6 小时和 24 小时的站点负荷与空闲桩数量。
6. 将预测结果用于用户端低拥堵站点推荐和管理端负荷预警。
7. 保证新增系统不破坏第一阶段实时充电、计费、交易和设备控制链路。

## 3 系统范围与总体架构

### 3.1 系统组成

接入完成后的平台由以下部分组成：

| 层级 | 组件 | 主要职责 |
| --- | --- | --- |
| 业务终端 | Qt 用户端 | 找桩、预约、充电、结算，并展示预测拥堵程度和推荐结果 |
| 业务终端 | Qt 管理端 | 实时运营管理，并展示预测负荷和负荷预警 |
| 实时业务层 | Qt C++ 服务端 | 身份认证、业务处理、实时推送、统一权限校验和客户端接口适配 |
| 业务数据层 | SQLite 与 UrbanEV 数据 | 保存第一阶段核心业务数据和站点、电桩基础数据 |
| 大数据处理层 | Hadoop HDFS、PySpark、SparkSQL | 数据接入、质量检测、清洗、分层存储和指标计算 |
| 智能分析层 | Spark MLlib | 模型训练、评估、预测和模型文件管理 |
| 分析服务层 | Flask API | 向 Web 大屏和 Qt 服务端提供只读分析接口 |
| 展示层 | Vue 与 ECharts Web 大屏 | 展示运营健康度、数据质量、模型指标和预测结果 |

### 3.2 总体数据流

```text
SQLite 业务数据与 UrbanEV 基础数据
              ↓
       数据快照或批量导出
              ↓
       原始数据与模拟脏数据
              ↓
   PySpark 质量检测与数据清洗
              ↓
  ODS → DWD → DWS → ADS 分层加工
              ↓
       ┌──────┴─────────┐
       ↓                ↓
Flask API → Web 大屏   Spark MLlib 训练与预测
                            ↓
                  ADS 预测结果与模型指标
                            ↓
               Flask API → Qt C++ 服务端
                            ↓
              Qt 用户端推荐与管理端预警
```

### 3.3 集成原则

- 第一阶段服务端仍是账户、钱包、预约、订单、计费和设备控制的唯一业务入口。
- Web 大屏和机器学习子系统原则上只读业务数据，不直接修改第一阶段业务表。
- 用户端和管理端不应绕过 Qt 服务端直接访问 Flask 分析服务。
- 实时交易数据和离线分析数据应隔离，分析任务失败不得阻断充电主流程。
- 跨系统接口应有版本、超时、错误响应和降级策略。
- 演示数据、模拟数据和真实业务数据应具有明确标识，避免统计口径混用。

## 4 用户角色与使用场景

### 4.1 充电用户

充电用户使用 Qt 用户端查询附近站点、查看电桩、预约和充电。接入预测能力后，用户应能查看站点未来负荷趋势、预计空闲桩数量和推荐理由，并优先选择低拥堵、高空闲率的站点。

### 4.2 运营管理员

运营管理员使用 Qt 管理端处理站点、电桩、订单、用户和告警。接入智能分析后，管理员应能查看短期负荷预测、高峰时段和预警站点，提前安排运维值守和资源调度。

### 4.3 运营决策者

运营决策者通过 Web 大屏查看全局运营健康度，包括营收、订单、充电电量、设备状态、告警、区域贡献、数据质量和模型效果，为运营决策提供依据。

### 4.4 系统维护人员

系统维护人员负责数据流水线、HDFS、模型、Flask 服务和大屏的运行检查，能够定位数据源缺失、处理失败、模型文件不可用和接口异常等问题。

## 5 现有平台能力边界

第二阶段应复用第一阶段已经定义的用户、管理员、站点、电桩、收藏、预约、订单、钱包流水、告警、控制记录和推送记录等业务实体。新增模块不得改变以下规则：

- 金额使用整数分保存和传输，展示层按元转换。
- 用户身份和管理员身份从已认证会话获取。
- 预约、开始充电、停止充电、结算和钱包扣费由第一阶段服务端执行事务控制。
- 客户端不因网络超时自行推断充电结束或结算成功。
- 电桩状态至少区分空闲、已预约、充电中、离线、故障和停用。
- 告警、设备控制和订单状态应保留可追踪关系。

第二阶段分析指标引用上述实体时，应通过稳定业务键建立关联，并保留来源标识和数据处理时间。

## 6 数据采集与源数据需求

### 6.1 数据源

| 需求编号 | 优先级 | 需求内容 | 验收要点 |
| --- | --- | --- | --- |
| DATA SRC 01 | P0 | 系统应接入用户、站点、电桩、订单、告警和天气数据 | 六类数据均能进入处理流程 |
| DATA SRC 02 | P0 | 系统应支持读取第一阶段现代 SQLite 数据库 | 能从业务库导出可分析快照 |
| DATA SRC 03 | P0 | 当课程虚拟机 SQLite 版本无法解析原数据库时，应支持兼容 CSV 快照 | 切换后无需修改原业务数据库 |
| DATA SRC 04 | P0 | UrbanEV 站点和电桩数据应保留原始来源标识 | 可追溯至来源记录 |
| DATA SRC 05 | P1 | 天气和节假日数据应包含日期、温度、降雨和节假日标记 | 可按日期关联订单与负荷 |
| DATA SRC 06 | P1 | 数据接入应记录批次号、接入时间和来源 | 能定位每次流水线输入 |

### 6.2 模拟数据

- 系统应能够基于第一阶段表结构和 UrbanEV 基础数据生成可配置规模的模拟业务数据。
- 默认演示数据宜包含约 10 万条订单，并覆盖用户、站点、电桩、告警和天气数据。
- 模拟数据应体现早晚高峰、工作日、周末、节假日、天气和站点差异等规律，使模型能够学习合理的负荷变化。
- 系统应主动生成少量可识别的质量问题，用于验证质量检测和清洗能力。
- 模拟数据应与真实业务快照隔离，并在文件名、目录或元数据中标明数据性质。

## 7 数据质量检测与清洗需求

### 7.1 质量检测

| 需求编号 | 优先级 | 质量维度 | 检测要求 |
| --- | --- | --- | --- |
| DATA DQ 01 | P0 | 完整性 | 检测必填字段为空或缺失 |
| DATA DQ 02 | P0 | 唯一性 | 检测用户 ID、手机号、站点 ID、桩 ID 和订单号重复 |
| DATA DQ 03 | P0 | 有效性 | 检测手机号、日期时间、枚举、坐标和金额格式 |
| DATA DQ 04 | P0 | 参照完整性 | 检测订单和告警引用不存在的用户、站点或电桩 |
| DATA DQ 05 | P0 | 一致性 | 检测订单时间倒置、负时长和费用计算不一致 |
| DATA DQ 06 | P0 | 异常值 | 检测余额、价格、功率、电量、温度、电流等越界或极端值 |
| DATA DQ 07 | P1 | 报告输出 | 输出汇总报告、问题明细和各规则命中数量 |

质量报告应至少包含扫描总行数、问题数量、问题率、质量维度、规则编号、数据表、字段、业务键和问题说明。

### 7.2 数据清洗

- 系统应完成业务键去重、数据类型转换、统一时间格式和枚举标准化。
- 对可安全修复的缺失值或格式问题，应按明确规则修复，并记录修复方式。
- 订单费用应按照统一统计口径重新校验；无法确认的记录不得静默改写。
- 无法修复、违反外键关系或明显异常的数据应进入隔离区，不得进入可信 DWD 明细层。
- 清洗结果和隔离结果应分别输出，且能够关联至原始记录。
- 清洗过程应具有幂等性，同一输入批次重复执行不应产生重复有效记录。
- 系统应统计显式规则问题和清洗级联隔离数量，解释两类数字的差异。

## 8 数据存储与数仓分层需求

### 8.1 存储要求

- 原始、清洗、汇总和应用数据应保存到 HDFS 对应目录。
- 结构化分析数据宜使用 Parquet 格式，必要时同步导出 CSV 或 JSON 供展示和调试使用。
- 数据目录应按层级、主题和批次组织，不得将运行生成的大体量数据提交到 Git。
- 模型文件、指标和预测结果应保存到独立目录并可按版本追踪。

### 8.2 数仓分层

| 层级 | 主要内容 | 必须满足的要求 |
| --- | --- | --- |
| ODS | 原始用户、站点、电桩、订单、告警、天气 | 尽量保留原值，增加行标识、来源和接入时间 |
| DWD | 清洗后的可信明细 | 统一数据类型、业务键、枚举、金额和时间口径 |
| DWS | 主题汇总数据 | 至少包含站点日经营、城市日经营、站点小时负荷和用户价值主题 |
| ADS | 展示与模型应用数据 | 至少包含概览、营收趋势、站点排名、小时负荷、桩状态、告警、区域指标和预测结果 |

### 8.3 统计口径

- 营收只统计已完成且结算成功的有效订单。
- 充电电量以有效订单的结算电量为准。
- 设备数量按有效站点和有效电桩主数据统计。
- 空闲桩、故障桩、离线桩和停用桩应使用统一状态映射。
- 时间统计应明确时区和自然日边界。
- 所有金额指标应明确数据层使用分还是元，接口不得混用。
- 大屏、Qt 管理端和导出报表使用同一统计口径时，结果应一致。

## 9 大数据可视化大屏需求

### 9.1 展示方式

大屏应采用 Web 页面展示，使用 Vue 组织页面、ECharts 绘制图表、Flask 提供分析接口。前端依赖应能够离线加载，以适应课程虚拟机无外网或网络不稳定的环境。

### 9.2 页面功能

| 需求编号 | 优先级 | 功能 | 展示内容与交互 |
| --- | --- | --- | --- |
| VIS 01 | P0 | 运营概览 | 累计营收、充电电量、有效订单量、站点数和电桩数 |
| VIS 02 | P0 | 营收趋势 | 展示近 30 日营收变化，支持日期提示 |
| VIS 03 | P0 | 电桩状态 | 展示空闲、充电中、故障、离线、停用等状态数量和占比 |
| VIS 04 | P0 | 小时负荷 | 展示全天小时级会话量或负荷曲线，标识高峰时段 |
| VIS 05 | P0 | 站点排名 | 按营收、订单量、充电量或利用率展示重点站点 |
| VIS 06 | P0 | 区域指标 | 展示各区域站点、订单、营收和贡献占比 |
| VIS 07 | P0 | 告警分布 | 按类型、级别或处理状态展示告警分布 |
| VIS 08 | P0 | 数据质量 | 展示扫描行数、问题数、问题率和规则分类 |
| VIS 09 | P0 | 负荷预测 | 展示未来 1、6、24 小时的站点负荷和预计空闲桩 |
| VIS 10 | P0 | 模型指标 | 展示模型名称、版本、训练时间、RMSE、MAE、R² 和主要特征重要性 |
| VIS 11 | P1 | 自动刷新 | 按配置周期刷新数据，失败时保留最近一次成功数据 |
| VIS 12 | P1 | 全屏适配 | 适配常用 16 比 9 屏幕和浏览器全屏展示 |
| VIS 13 | P1 | 状态提示 | 清晰展示加载中、空数据、数据过期和接口异常状态 |

### 9.3 可视化规范

- 页面应保持统一的配色、字号、间距和图表样式。
- 图表标题、图例、坐标轴、单位和提示信息应完整且无重叠。
- 数量、金额、比例、功率、电量和时间应显示明确单位。
- 不得使用颜色作为唯一状态区分方式，关键状态还应有文字或图标提示。
- 图表数据不足时应显示空状态，不得绘制误导性趋势。
- 模型指标较差时仍应如实展示，不得隐藏或夸大模型效果。

## 10 机器学习智能分析子系统需求

### 10.1 预测目标

系统应以站点为预测对象，预测未来 1 小时、6 小时和 24 小时内的以下指标：

- 充电会话数或等价负荷指标。
- 预计空闲充电桩数量。
- 高峰充电时段。
- 站点拥堵等级或负荷预警等级。

### 10.2 特征要求

基础模型特征至少包括：

- 站点标识。
- 小时和星期。
- 工作日、周末和节假日标记。
- 温度和降雨。
- 充电价格。
- 电桩总数和快充桩数。
- 故障、离线或停用桩数量。
- 历史小时负荷或订单量。

新增特征应能够解释来源、含义、单位和缺失值处理方式，禁止直接使用未来时刻才能获得的数据造成数据泄漏。

### 10.3 模型训练与评估

| 需求编号 | 优先级 | 需求内容 | 验收要点 |
| --- | --- | --- | --- |
| ML 01 | P0 | 使用 Spark MLlib 完成可重复训练 | 脚本可独立或随流水线运行 |
| ML 02 | P0 | 基础版本支持随机森林回归模型 | 能输出模型目录与预测结果 |
| ML 03 | P0 | 训练集和测试集应按时间或明确规则划分 | 无明显未来数据泄漏 |
| ML 04 | P0 | 输出 RMSE、MAE、R² 和特征重要性等评估结果 | 接口和大屏能够读取 |
| ML 05 | P0 | 每条预测应包含站点、预测时间、预测范围和生成时间 | 可识别 1、6、24 小时结果 |
| ML 06 | P0 | 预测空闲桩数量应限制在 0 至站点有效桩数范围内 | 不出现负数或超过总桩数 |
| ML 07 | P1 | 保存模型版本、特征版本和训练批次 | 可以追踪预测来源 |
| ML 08 | P1 | 模型不可用时回退到历史统计或最近一次有效结果 | 用户端和管理端不阻断 |
| ML 09 | P2 | 支持与线性回归、梯度提升树等基线模型比较 | 记录统一评估指标 |

### 10.4 预测结果要求

- 预测值应提供明确单位并按业务需要取整或保留小数。
- 预测记录应包含 `stationId`、`horizonHours`、`predictedSessions`、`predictedAvailablePiles`、`predictedPeakPeriod`、`generatedAt` 和 `modelVersion` 等核心字段。
- 预测结果应写入 ADS 应用数据层，并通过 Flask API 提供查询。
- 预测生成时间超过配置阈值时，接口应标识数据已过期。
- 模型评估指标低于项目设定阈值时，应展示风险提示，但不应伪造或修饰结果。

## 11 Flask 分析接口需求

### 11.1 现有大屏接口基线

分析服务至少应提供以下只读接口：

| 接口 | 用途 |
| --- | --- |
| `GET /api/health` | 服务健康检查和数据更新时间 |
| `GET /api/overview` | 全局运营概览 |
| `GET /api/revenue-trend` | 营收趋势 |
| `GET /api/station-rank` | 站点经营排名 |
| `GET /api/hourly-load` | 小时负荷 |
| `GET /api/pile-status` | 电桩状态分布 |
| `GET /api/alarm-distribution` | 告警分布 |
| `GET /api/district-metrics` | 区域指标 |
| `GET /api/quality` | 数据质量报告 |
| `GET /api/predictions` | 站点负荷预测 |
| `GET /api/model-metrics` | 模型评估指标 |

### 11.2 通用响应要求

所有接口应返回结构化 JSON，并统一包含以下语义：

```json
{
  "success": true,
  "data": {},
  "message": "",
  "generatedAt": "2026-09-15T10:00:00+08:00",
  "dataVersion": "batch-or-version"
}
```

错误响应应返回可识别的 HTTP 状态码和错误信息，不得向调用方暴露服务器路径、堆栈、数据库连接信息或敏感配置。

### 11.3 查询参数

- 趋势和明细接口宜支持 `startDate`、`endDate` 或预设时间范围。
- 站点相关接口应支持 `stationId`，多个站点查询应限制数量上限。
- 预测接口应支持 `horizonHours=1|6|24`。
- 排名接口应支持 `metric` 和受控的 `limit` 参数。
- 无数据时应返回成功和空集合，不应将无数据视为服务器异常。

## 12 Qt 平台接入需求

### 12.1 接入方式

Qt 用户端和管理端应继续通过现有 TCP 协议连接 Qt C++ 服务端。Qt C++ 服务端作为分析接口适配层，调用 Flask API、进行响应校验、缓存和降级，再通过公共消息协议返回客户端。

基础版本不要求 Flask 主动写入 SQLite，也不要求 Qt 客户端直接访问 Flask。

### 12.2 公共协议扩展

应在公共消息协议中增加或确认以下消息语义，具体枚举值由实现阶段统一分配：

| 功能 | 请求 | 响应或推送 |
| --- | --- | --- |
| 站点负荷预测查询 | `LoadPredictionRequest` | `LoadPredictionResponse` |
| 低拥堵站点推荐 | `StationRecommendationRequest` | `StationRecommendationResponse` |
| 管理端负荷预警查询 | `LoadWarningRequest` | `LoadWarningResponse` |
| 负荷预警状态变化 | 无或订阅请求 | `LoadWarningPush` |
| 模型与数据状态查询 | `AnalyticsStatusRequest` | `AnalyticsStatusResponse` |

新增消息应继续遵守协议版本、非零 `requestId`、响应原样返回 `requestId`、会话鉴权、长度校验、统一错误码和超时处理等现有规则。

### 12.3 用户端低拥堵站点推荐

| 需求编号 | 优先级 | 需求内容 |
| --- | --- | --- |
| INT USER 01 | P0 | 用户查询附近站点时，服务端应能够附加未来负荷和预计空闲桩信息 |
| INT USER 02 | P0 | 用户端应支持按低拥堵程度推荐站点，同时保留距离、价格和当前空闲桩信息 |
| INT USER 03 | P0 | 推荐结果应显示预测范围和预测生成时间，避免被误认为实时状态 |
| INT USER 04 | P0 | 预测不可用时应回退到现有站点排序，找桩和充电主流程仍可使用 |
| INT USER 05 | P1 | 推荐理由应简明说明距离、当前空闲情况和预测拥堵程度 |
| INT USER 06 | P1 | 用户刷新或切换 1、6、24 小时范围时，应重新获取对应结果 |

推荐算法不得只依据预测负荷。基础排序宜综合距离、当前可用桩数、预测空闲桩数、价格、站点可用状态和预测时效性。

### 12.4 管理端负荷预警

| 需求编号 | 优先级 | 需求内容 |
| --- | --- | --- |
| INT ADMIN 01 | P0 | 管理端应展示未来 1、6、24 小时重点站点负荷 |
| INT ADMIN 02 | P0 | 系统应按可配置阈值生成正常、关注、拥堵和严重等预警等级 |
| INT ADMIN 03 | P0 | 预警应包含站点、时间范围、预测会话数、预计空闲桩和生成时间 |
| INT ADMIN 04 | P0 | 预测服务异常时应显示数据不可用或已过期，不得展示为正常 |
| INT ADMIN 05 | P1 | 管理端可按预警等级、区域和预测范围筛选 |
| INT ADMIN 06 | P1 | 同一站点同一预测范围的重复预警应合并或更新，避免重复弹窗 |
| INT ADMIN 07 | P2 | 可将预警与值守安排、维护计划或站点扩容分析关联 |

负荷预警属于决策支持信息，不得自动触发停止充电、停用电桩、扣费或其他高风险业务操作。

### 12.5 服务端适配与缓存

- Qt 服务端调用 Flask API 时应设置连接超时和整体请求超时。
- 服务端应校验 HTTP 状态、JSON 格式、字段类型、数据版本和生成时间。
- 可缓存最近一次有效的预测和指标数据，并明确标记缓存时间。
- Flask 不可用时，服务端应返回统一的分析服务不可用错误，不得影响其他业务消息处理。
- 服务端应限制单次查询站点数量和请求频率，防止分析接口拖慢实时业务线程。
- 分析服务调用宜在线程池或异步任务中执行，不应阻塞 Socket 收发线程。

## 14 非功能需求

### 14.1 性能

- 在课程演示数据规模下，完整流水线应能够一次执行成功，并输出各层数据、模型和 ADS 结果。
- 大屏普通聚合接口在服务正常、数据已生成时，宜在 2 秒内返回。
- 大屏首屏在局域网环境下宜在 5 秒内完成主要内容展示。
- Qt 预测查询宜在 3 秒内返回；超时后应降级，不得持续阻塞界面。
- 大屏自动刷新不应触发完整模型训练或完整数仓重算。

### 14.2 可靠性

- 流水线单个阶段失败时应返回非零状态并输出清晰日志。
- 失败任务不得覆盖上一批可用结果。
- 重复执行同一批次应保持结果可重复，不产生重复记录。
- Flask 服务启动时应检查关键数据文件是否存在，并通过健康接口报告状态。
- 大屏和 Qt 客户端应区分服务异常、空数据和数据过期。

### 14.3 兼容性

- 大数据运行环境应兼容项目指定的 Hadoop、Spark 和 Python 版本。
- Web 大屏应支持课程验收使用的主流 Chromium 内核浏览器。
- 中文字体、图表标签、窗口缩放和全屏模式应通过视觉检查。
- Vue 和 ECharts 资源应可离线加载，不依赖公共 CDN。

### 14.4 可维护性

- 数据生成、质量检测、清洗、数仓加工、模型训练和大屏启动应提供独立脚本。
- 关键阈值、数据路径、服务地址和端口应集中配置，不应散落硬编码。
- 各处理阶段应输出开始时间、结束时间、输入规模、输出规模和错误原因。
- 接口字段、统计口径、模型特征和目录结构应有文档说明。

## 15 部署与运行需求

### 15.1 大数据环境

- Hadoop 的 HDFS 和 YARN 应可正常启动和读写。
- HDFS 应包含 `/charging_platform/ods`、`/charging_platform/dwd`、`/charging_platform/dws`、`/charging_platform/ads` 和 `/charging_platform/models` 等目录。
- 不得通过重新格式化 NameNode 解决普通启动问题。
- 环境检查脚本应验证 Java、Hadoop、Spark、Python、HDFS 和必要目录。

### 15.2 应用部署

- Flask、Vue 和 ECharts 应位于 `bigdata/dashboard` 或等价明确目录。
- 演示环境可使用 Flask 内置服务器，长期部署宜使用 Gunicorn 等 WSGI 服务。
- 服务地址变化时应通过配置修改，Qt 客户端和服务端不得依赖固定虚拟机 IP。
- `bigdata/data` 和 `bigdata/logs` 等生成目录不得提交到 Git。
- 项目应提供一键或分步运行说明，能够完成环境检查、流水线执行、大屏启动和停止。

## 16 异常处理与降级需求

| 场景 | 系统行为 |
| --- | --- |
| SQLite 无法直接读取 | 自动或按说明切换到兼容 CSV 快照，不修改原数据库 |
| 输入文件缺失 | 终止对应阶段，记录缺失文件和批次，不生成伪造结果 |
| 数据质量问题过多 | 输出报告并按阈值阻断可信层写入或标记批次不可用 |
| HDFS 或 YARN 不可用 | 流水线失败并保留上一批有效结果 |
| 模型训练失败 | 保留上一版本模型和预测，接口标记结果时间与版本 |
| 模型文件缺失 | Flask 健康接口报告降级，预测接口返回明确错误 |
| Flask 服务不可用 | Web 大屏显示异常；Qt 服务端使用缓存或回退到非预测功能 |
| 预测结果过期 | 大屏和 Qt 客户端明确标识过期，不作为实时状态展示 |
| 单个图表接口失败 | 其他图表继续展示，失败区域提供重试入口 |
| Qt 分析查询超时 | 结束本次请求并返回统一错误，不影响充电与计费流程 |

## 17 测试与验收需求

### 17.1 数据流水线验收

- 模拟数据生成脚本能够按配置生成所有必要数据表。
- 质量检测覆盖完整性、唯一性、有效性、参照完整性、一致性和异常值。
- 清洗能够去重、转换、修复、校验并输出隔离数据。
- ODS、DWD、DWS、ADS 四层均产生预期表或文件。
- HDFS 和本地导出结果的关键记录数、字段和指标可核对。
- 流水线重复运行不会产生非预期重复数据。

### 17.2 模型验收

- 训练脚本可运行并保存模型。
- 能为配置的重点站点生成 1、6、24 小时预测。
- 每条结果包含站点、预测范围、预测值、生成时间和模型版本。
- RMSE、MAE、R²、特征重要性和测试样本规模能够输出并被接口读取。
- 预测空闲桩数量不小于 0 且不大于有效桩数。
- 使用人工构造的高峰、降雨或设备不可用场景验证模型输入和输出方向合理。
- 若模型效果未达到预期，应保留真实指标，并在验收报告中说明限制和优化方向。

### 17.3 Flask API 验收

- `/api/health` 返回服务状态、数据状态和更新时间。
- 十类业务指标接口和模型指标接口均完成成功、空数据、参数错误和文件缺失测试。
- JSON 字段、单位、时间格式和错误格式保持一致。
- 非法站点、非法预测范围和超大查询范围被正确拒绝。
- 接口不暴露堆栈、文件路径和敏感配置。

### 17.4 Web 大屏验收

- 所有指标卡和图表均有数据时正常渲染。
- 无数据、加载中、接口失败和数据过期状态清晰可见。
- 在目标屏幕尺寸、浏览器缩放和全屏模式下无裁切、重叠、乱码和不可读标签。
- 图表数值与 ADS 数据及接口响应抽样一致。
- 页面离线环境下不请求公共 CDN。
- 自动刷新不会造成明显闪烁、图表重复创建或浏览器持续增大内存占用。

### 17.5 Qt 联动验收

- 用户端能够查看预测范围、预计空闲桩和低拥堵推荐。
- 管理端能够查看重点站点负荷和预警等级。
- Qt 服务端正确处理 Flask 成功、超时、无数据、无效 JSON 和过期数据。
- Flask 停止后，用户仍可完成原有找桩、预约、充电和结算流程。
- 分析请求不会阻塞实时充电推送和管理员控制消息。
- 新增 TCP 消息完成正常、未登录、越权、参数非法、重复请求和超时测试。

### 17.6 基础验收通过条件

满足以下条件时，第二阶段基础版本可判定通过：

1. 完整流水线可从源数据运行到 ADS 和模型预测结果。
2. 六类数据质量检测和隔离机制可验证。
3. ODS、DWD、DWS、ADS 层级和关键主题数据齐全。
4. Web 大屏核心指标和图表完成接口与视觉验收。
5. 模型能输出未来 1、6、24 小时预测和真实评估指标。
6. Qt 用户端推荐、管理端预警至少完成接口联调和降级验证。
7. 新增能力不破坏第一阶段业务回归测试。
8. 项目提交包含源码、运行说明、测试记录、数据质量报告、数仓说明和演示材料。
